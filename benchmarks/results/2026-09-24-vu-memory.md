# 2026-09-24 — Memory per VU

Environment: i5-1235U, 15.7 GB, Windows 11, go1.27.0. The laptop was not
isolated.

This is **not** a JMeter comparison and does not show the Phase 0 exit
criterion.

## 1. Heap retained per VU (in-process)

```bash
go test -run='^$' -bench=VURetainedMemory -benchtime=5x -count=3 ./internal/script/
```

The benchmark creates 1,000 VUs from a TypeScript script, forces two GC
cycles, and divides the live-heap growth by 1,000. It counts the VU's goja
runtime only. Goroutine stacks and HTTP connections are excluded.

| State | retained-B/VU (3 runs) |
|---|---|
| after init | 29,904 / 29,909 / 29,904 |
| after first iteration | 29,776 / 29,776 / 29,776 |

The runtime does not grow after the first iteration, so 1,000 VUs retain
about **29 MB** of heap.

### Where it goes

A heap profile taken while 1,000 VUs were alive showed about 83% allocated
under `goja.(*Runtime).RunProgram`, i.e. while the script's top-level code
ran. A one-off experiment compared the retained size for different top-level
code:

| Top-level code | retained B/VU |
|---|---|
| esbuild CommonJS output of `export default function () {}` (current) | 29,654 |
| Hand-written `module.exports = { default: function () {} }` | 7,048 |
| Same, plus reading `Object.defineProperty` | 8,312 |
| Bare `goja.New()` | 1,712 |

About 22 KB per VU (roughly 75%) comes from esbuild's generic CommonJS
interop helpers (`__export`, `__copyProps`, `__toCommonJS`), which every
VU's runtime executes. This was fixed afterwards; see section 3.

## 2. Whole-process peak memory

```powershell
./benchmarks/loadtool/peak-memory.ps1 -Script cpu.ts -VUs <n> -Duration 10s
```

`cpu.ts` makes no HTTP requests, so the target server's connection limits
(see [2026-09-24-script-execution.md](2026-09-24-script-execution.md))
cannot affect the result:

```typescript
export default function (): void { let t = 0; for (let i = 0; i < 1000; i++) t += i; }
```

| VUs | peak working set (3 runs) | peak private bytes (3 runs) |
|---|---|---|
| 1 | 21.0 / 72.2 / 72.2 MB | 55.5 / 55.4 / 55.6 MB |
| 1000 | 233.6 / 268.4 / 259.6 MB | 228.1 / 252.0 / 243.3 MB |

A `GODEBUG=gctrace=1` run at 1,000 VUs showed:

- **Live heap after GC:** 35–63 MB (29 MB of VU runtimes plus in-flight
  iteration garbage).
- **Heap at GC start:** up to about 110 MB. The heap overshot the GC goal,
  because 1,000 VUs allocate while the concurrent GC runs.
- **Goroutine stacks:** 1–2 MB for all 1,000 VUs.

### Findings

- The difference between 1 and 1,000 VUs (about 175–195 MB of private
  bytes) is much larger than the retained VU state (29 MB). Most of it is
  GC headroom and freed memory not yet returned to the OS. That is driven
  by how fast the script allocates, and this script allocates constantly
  because every VU runs a tight CPU loop.
- **Process peak memory depends on the workload, not only on the VU
  count.** For the JMeter comparison, the scenario (request rate, server
  latency, think time) must be identical between tools and recorded, and
  `GOGC` / `GOMEMLIMIT` must be at their defaults or stated explicitly.
- The 1-VU working-set values vary (21 vs 72 MB) because Windows reports
  working set as pages currently resident, which depends on OS paging.
  Private bytes were stable, so they are the better number for
  comparisons.

## 3. After removing the CommonJS interop helpers

Scripts are now bundled behind a generated entry
(`import fn from "<script>"; globalThis.__loadtool_default = fn;`), so
esbuild binds the default export directly and emits no interop helpers
(guarded by `TestTranspileHasNoInteropHelpers`). Same machine and commands
as above.

### Per VU

| Benchmark | Before | After |
|---|---|---|
| `BenchmarkVURetainedMemory/after-init` (retained-B/VU, 3 runs) | 29,904 / 29,909 / 29,904 | **5,984 / 5,989 / 5,984** |
| `BenchmarkVURetainedMemory/after-first-iteration` | 29,776 (×3) | **6,032 (×3)** |
| `BenchmarkNewVU` B/op, allocs/op | 39,610, 458 | **6,144, 54** |

Retained heap per VU fell by about 80%. 1,000 VUs now retain about 6 MB
instead of 29 MB.

### Iteration cost (unchanged)

Old (`5d2d001`) and new test binaries were run alternately, 3 rounds:

| Benchmark | old ns/op | new ns/op | allocs/op (both) |
|---|---|---|---|
| `BenchmarkIterateEmpty` | 393.3 / 366.0 / 348.3 | 353.8 / 372.2 / 389.2 | 4 |
| `BenchmarkIterateHTTPGet` | 151,175 / 133,767 / 123,937 | 135,223 / 131,957 / 152,190 | 90 |

No difference beyond run-to-run noise. A separate non-alternating run
earlier in the session measured about 600 ns and 270–310 µs for the new
code, and the alternating A/B showed that was machine load at the time,
not the change.

### Whole process, 1,000 VUs, `cpu.ts`

| | Before | After |
|---|---|---|
| Peak private bytes (3 runs) | 228.1 / 252.0 / 243.3 MB | **132.1 / 113.8 / 97.9 MB** |
| Peak working set (3 runs) | 233.6 / 268.4 / 259.6 MB | **133.8 / 131.5 / 114.9 MB** |
| Live heap after GC (gctrace) | 35–63 MB | 12–16 MB |
| Heap at GC start (gctrace) | up to ~110 MB | up to ~36 MB |
| GC cycles in a 5 s run | 26 | 138 |
| GC CPU fraction (gctrace) | 8% | 11% |

The 1-VU baseline did not change (peak private 55.0 / 55.3 / 55.2 MB).

- The process peak fell by much more than the 23 MB of VU state saved.
  Go's GC sets its heap goal from the live heap (about 2× with the default
  `GOGC=100`), so a smaller live heap also shrinks the headroom.
- Trade-off: with a smaller heap goal, the GC runs more often. On this
  allocation-heavy CPU-loop script its CPU share rose from 8% to 11%.
  Scripts that make HTTP requests allocate far less per second per VU;
  that case has not been measured.
